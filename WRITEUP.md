# Write-up

## Schema reasoning

The relational chain follows the spec directly: `organizations → org_members → workflows → workflow_steps` / `workflow_triggers`, and `workflows → workflow_runs → step_runs`. One deliberate deviation: **`org_id` is denormalized directly onto `workflow_runs`**, rather than only reachable by joining up through `workflow_id → workflows.org_id`. Every permission rule and every isolation check ultimately needs to answer "does this row belong to an org the caller is in," and having `org_id` sit directly on the run row makes that check a single hop instead of a multi-table join repeated across every permission rule on `workflow_runs` and (transitively) `step_runs`. It also matches how the Action handler naturally has `org_id` in hand at run-creation time, so writing it once at creation costs nothing.

`step_runs.attempt`, `approved_by`, and `approved_at` exist specifically because the assignment calls out retry tracking and the approval audit trail as first-class requirements, not afterthoughts to bolt on — better to have the columns from the start than migrate them in later.

## The two permission layers, and why they're enforced differently

**Layer 1 (org + role scoping)** is enforced entirely declaratively, as Hasura row-level permissions. Every table's select/insert/update/delete permission for Hasura role `user` includes a check that traces back to `org_members.user_id = X-Hasura-User-Id`, walking whatever relationship chain connects that table to an org (direct on some tables, through `workflow_id` or `workflow_run_id` on others). This is a pure "can this row be seen/touched by this caller at all" question, which is exactly what a database-level row filter is for — it's checked on every single query automatically, can't be bypassed by forgetting to add a check in application code, and composes correctly even for nested GraphQL queries.

One important implementation detail: Hasura's actual JWT role for every authenticated request is just `user` (nhost's default), not a literal `owner`/`editor`/`viewer` Hasura role — the org-specific role lives as *data* in `org_members.role`, not as a JWT claim. So Layer 1's permission JSON for the `user` role folds role differentiation directly into the check itself (e.g. insert permission requires `org_members.role IN ('owner','editor')`) rather than relying on separate Hasura roles per org-role.

**Layer 2 (step-level gating)** is split across two different mechanisms because it's two different kinds of decision. The declarative half — blocking `editor` from creating `db_write`/`notify` steps or `webhook` triggers — is still a simple row-level check (does this insert's `type` column match a restricted value), so it's expressed the same way as Layer 1, just with an added `type NOT IN (...)` condition.

The procedural half — clearing an `approval_gate` — genuinely cannot be a database permission, because it isn't a row-write authorization question; it's "is this specific paused run, for this specific step, allowed to be resumed by this specific caller, right now." That requires looking up current state (is the step actually still paused, not already resolved), checking the caller's live role from `org_members`, and then performing a multi-step side effect (mark approved, resume execution, potentially run several more steps). A Hasura permission has no vocabulary for "resume execution" — so this logic lives in the `approveStep` Action handler's code, which re-queries `org_members` fresh on every call rather than trusting a JWT claim or a cached role. This is checked and verified: a `viewer`'s approval attempt is rejected with a 403 from inside the handler, independent of and in addition to whatever Layer 1 permission might otherwise apply to the mutation call itself.

## Approval-gate pause/resume implementation

`triggerWorkflowRun` executes `workflow_steps` sequentially in a loop. On hitting a step with `type = 'approval_gate'`, it inserts a `step_runs` row with `status = 'paused_awaiting_approval'`, sets the parent `workflow_runs.status = 'paused'`, and returns immediately — the function does not block or poll; execution genuinely stops.

`approveStep` is a separate Action, called later (potentially much later, by a different request entirely) with a `step_run_id`. It: (1) loads the step_run and confirms its status is actually `paused_awaiting_approval` (rejecting stale/already-resolved approval attempts), (2) re-checks the caller's org membership and role, (3) marks that step_run `succeeded` with `approved_by`/`approved_at` set, (4) sets the parent run back to `running`, (5) queries for all `workflow_steps` with `step_order` greater than the approved step's, and (6) continues the exact same step-execution loop from `triggerWorkflowRun` against those remaining steps — including handling a second `approval_gate` if one exists further down the chain, and marking the run `completed` once the loop exhausts.

Because every status write happens as a GraphQL mutation against Hasura (not a raw SQL write bypassing it), any client subscribed to `step_runs` for that `workflow_run_id` sees each status change live, in order, with no polling and no page refresh — verified end-to-end through the deployed frontend: trigger → three steps stream to `succeeded` → the fourth shows `paused_awaiting_approval` with an Approve button → clicking it resumes and completes, all visible in the same open browser tab.
